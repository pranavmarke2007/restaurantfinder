1. Project Overview

Restaurant Finder is a full-stack web application that helps users discover nearby restaurants personalized to their taste preferences. When a user travels to a new city, the app finds restaurants near them and uses AI to match those restaurants against their local food preferences — giving each restaurant a personalized match score.

Core Value Proposition: "Your taste, anywhere in the world." — Match local food preferences to restaurants in any new city using AI.

4. How the Server Works

4.1 Custom HTTP Server (No Express)

Built from scratch using Node.js's native http.createServer(). It handles two types of requests:

  • API requests (URL starts with /api/) → routed to handleApi()
  • Static file requests (everything else) → routed to serveStatic() which reads files from disk with correct MIME types

4.3 Authentication System

  • Password hashing: PBKDF2 algorithm with SHA-512, 120,000 iterations, and a random 16-byte salt per user
  • Session management: Token-based. On login/signup, a 32-byte random hex token is generated and stored in the database
  • Timing-safe comparison: Uses crypto.timingSafeEqual() to prevent timing attacks on password verification
  • No JWT: Sessions are simple database lookups — token → userId → user object

4.4 Database Strategy (Dual-Layer)

The app has a graceful degradation pattern for the database:

  1. Primary: MongoDB Atlas (cloud) — via Mongoose ODM with schemas for User and Session
  2. Fallback: Local database.json file — if MongoDB connection fails, the app automatically switches
  3. Auto-reconnect: If MongoDB disconnects during runtime, the server retries every 15 seconds automatically

4.5 AI Integration — Google Gemini

The /api/ai/recommend endpoint works as follows:

  1. Receives the user's preferences + the list of nearby restaurants
  2. Constructs a detailed prompt describing the user as a traveler looking for culinary matches
  3. Sends it to Gemini 2.0 Flash with responseMimeType: "application/json" to force structured JSON output
  4. Gemini returns match scores (0–100) and personalized reasons for each restaurant
  5. If Gemini fails or no API key is set, the app falls back to a local text-based scoring algorithm

5.3 Restaurant Discovery — Overpass API

The app sends an Overpass QL query to OpenStreetMap to find all nodes/ways/relations tagged as amenity=restaurant within 5000 meters of the user's coordinates. This returns structured data including name, cuisine type, address, coordinates, and any images tagged on OpenStreetMap.

5.7 Distance Calculation

Uses the Haversine formula to calculate straight-line (great-circle) distance between two latitude/longitude points on Earth's surface. Earth radius = 6,371 km.

8. Key Design Patterns & Approaches

8.1 Graceful Degradation

Every external dependency has a fallback:

  • MongoDB → JSON file
  • Gemini AI → local scoring algorithm
  • 3 geocoding providers tried in sequence
  • 4-tier image resolution pipeline

8.2 Zero-Framework Backend

No Express, no Fastify. Pure Node.js http module. Zero middleware, full control over request handling, and minimal dependencies.

8.3 Single-Page App Without a Framework

Vanilla JS with direct DOM manipulation. No React, no Vue. Dialogs use the native HTML <dialog> element.

8.4 Dual Scoring Engine

AI scoring (Gemini) for personalization + local text-based scoring as fallback. The hybrid sort combines match quality with proximity.

8.5 Preference Normalization

All preference lists go through normalizePreferences() — ensures consistent structure (name + weight), removes empties, clamps weights 1–5, and generates a taste signature string.

8.6 Other Patterns

  • Debounced Autocomplete — 300ms debounce to avoid excessive API calls
  • Image Caching — Map-based cache prevents re-fetching images
  • Taste Signature — Concatenated string of all preferences for semantic comparison
